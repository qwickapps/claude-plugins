# Executing Plans

## Overview

Load an implementation plan, review it critically, execute tasks in batches, and report for review between batches. The core principle is batch execution with checkpoints: work a defined set of tasks, stop, report what was done, wait for feedback, then continue.

Announce at the start: "I'm using the executing-plans skill to implement this plan."

## The Process

### Step 1: Load and Review the Plan

Read the plan file from `docs/plans/YYYY-MM-DD-<feature-name>.md`.

Review critically before starting any work. Look for:
- Steps that reference files which do not exist yet
- Test commands that assume dependencies are installed
- Implementation steps that conflict with observed codebase state
- Ambiguous instructions that could be interpreted more than one way
- Tasks out of order relative to their dependencies

**If concerns exist:** Raise them before executing any task. List the specific issues. Ask whether to proceed with the plan as written, update the plan, or adjust the approach.

**If no concerns exist:** Create a task list from the plan and proceed to Step 2.

### Step 2: Execute a Batch

The default batch size is 3 tasks. For each task in the batch:

1. Mark the task as in_progress using TaskUpdate
2. Execute each step in the task exactly as written in the plan
3. Run verifications as specified — do not skip them
4. Mark the task as completed using TaskUpdate

Execute steps literally. The plan was written to be followed as written. Do not substitute alternative implementations, skip steps that seem redundant, or combine steps to save time.

**Following steps exactly means:**
- If the plan says "run this specific test command," run that specific command
- If the plan says "write a failing test first," write the test before any implementation
- If the plan says "commit after this step," commit after that step — not at the end of the batch

### Step 3: Report

When the batch is complete, report what was done:

- List each task completed
- Include the verification output for each task (test results, build output, or other specified verification)
- Note any deviations from the plan (even small ones)

Close the report with: "Ready for feedback."

Then stop. Do not begin the next batch. Wait for the review.

### Step 4: Continue

Based on feedback:

- Apply any requested changes before proceeding
- If the feedback modifies the plan, update the plan document and re-read the affected tasks
- Execute the next batch

Repeat Steps 2 through 4 until all tasks are complete.

### Step 5: Complete Development

After all tasks are complete and verified, transition to branch finalization:

Announce: "All plan tasks complete. Invoking finishing-branch to finalize this development branch."

Invoke sdlc:finishing-branch to handle test verification, PR preparation, and branch completion.

## Batch Size

The default is 3 tasks per batch. Adjust when:

**Smaller batches (1-2 tasks):**
- High-risk tasks (database migrations, infrastructure changes, security-sensitive code)
- Tasks with many unknowns or external dependencies
- Early in execution when the plan is unproven

**Larger batches (4-5 tasks):**
- Mechanical, low-risk work (adding test cases following an established pattern, updating constants)
- After several successful batches have confirmed the plan is accurate

The executor decides the batch size unless the plan specifies otherwise or the user requests a specific size.

## When to Stop and Ask

Stop executing immediately and ask for guidance when:

- A blocker appears mid-batch: a file that should exist does not, a dependency is not installed, a test environment is unavailable
- A verification fails repeatedly and the cause is not obvious from the plan
- A plan step is ambiguous and could reasonably be interpreted in two or more incompatible ways
- An assumption in the plan proves false (a library behaves differently than the plan assumes)
- A plan step conflicts with an observed constraint in the codebase

**Do not guess.** Do not implement an alternative interpretation of the step. Do not skip the problematic step and continue with the next one. Stop, report the exact issue with specific detail, and wait for direction.

**Example of correct blocker reporting:**

"Blocked on Task 4, Step 2. The plan says to run `pnpm run test:integration` but this command does not exist in `package.json`. The available test commands are: `test`, `test:unit`, `test:e2e`. Should I use `test:unit`, or does the plan need to be updated?"

**Example of incorrect behavior:**

Running `test:unit` without mentioning the discrepancy, or skipping the test step entirely.

## When to Revisit the Plan

Return to Step 1 (load and review) when:

- The user updates the plan in response to a blocker or feedback
- A fundamental assumption in the plan is invalidated during execution
- The user requests a change in approach that affects multiple tasks

Do not carry forward a mental "updated plan" without updating the document. The plan document is the source of truth.

## Tracking Progress

Use TaskUpdate to maintain an accurate task list throughout execution:

- Mark tasks `in_progress` when starting them
- Mark tasks `completed` when they are done and verified
- Never mark a task completed if its verification step failed

The task list is visible to the user. It should reflect actual state, not optimistic state.

## Branch Safety

Never execute a plan on the `main` or `dev` branch without explicit user confirmation. Plans are executed in dedicated worktrees. If the current branch is `main` or `dev`, stop and confirm before proceeding.

The creating-worktree skill exists to set up the correct isolated workspace. If no worktree is available, raise that before starting.

## Between Batches

After reporting and before starting the next batch:

- Wait for an explicit signal to continue ("looks good", "proceed", "continue", or equivalent)
- Do not interpret silence as approval
- Do not begin the next batch while waiting for review

If the user provides feedback that modifies the approach, update the plan document before continuing.

## Integration with Other Skills

**sdlc:writing-plans** — Creates the plan that this skill executes. The plan header references this skill by name to signal how it should be run.

**sdlc:creating-worktree** — Sets up the isolated workspace before plan execution begins.

**sdlc:finishing-branch** — Handles post-execution tasks: final test run, PR preparation, branch cleanup.

## Remember

- Review the plan critically before executing any task
- Follow plan steps exactly — do not substitute or skip
- Run verifications as specified — do not skip them
- Execute in batches; report and wait between batches
- Stop when blocked; do not guess through ambiguity
- Track progress with TaskUpdate throughout
- Never work on main or dev without explicit confirmation
